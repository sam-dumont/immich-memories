# The store: one versioned database on SQLite or PostgreSQL

Issue #871 holds the decision, the inventory with file:line and the dual-backend rules. This page is the
contract the code follows. When the two disagree, the issue's "Decision 2026-09-26" wins and this page is fixed.

## Two lifetimes

| | Store | Cache |
|---|---|---|
| Holds | human decisions, model answers someone paid for, run history, UI-edited settings | derived analysis, hashes, scene prints, geocoding |
| Backend | the configured URL: SQLite (default) or PostgreSQL | always local SQLite files |
| Schema changes | Alembic, one history for both backends | `PRAGMA user_version`; a mismatch drops and rebuilds |
| Backed up | yes (`store backup`) | no |

Media, previews, thumbnails and per-attempt artifacts stay files.

The cache is `cache.db` (video analysis and segments, the hash index, video metadata, the
look-failure ledger; `cache/analysis_schema.py`) plus `structure-banks/thumbnail-hashes.sqlite` and
`scene-prints.sqlite`, all opened through `connect_sqlite`. `cache.db` carries `CACHE_VERSION` in
`PRAGMA user_version`. The migration ladder it had (v1..v25) is gone: a file that ladder finished
(ledger at 25, no stamp) is adopted as it stands, so an upgrade keeps its analysis; any other
layout has its cache tables dropped and rebuilt empty. The store's old tables in an old `cache.db`
are never touched: the legacy import reads them.

## Package layout

- `immich_memories/db/`: engine, bootstrap URL, the SQLite connection factory, the network-filesystem guard,
  the upsert helper, time helpers, migration runner and lock, backup/restore (`backup.py`), copy
  (`copy.py`), status (`status.py`), per-table counts and digests (`inventory.py`).
- `immich_memories/db/tables/<domain>.py`: SQLAlchemy `Table` objects on one shared `MetaData(schema="immich_memories")`.
- `immich_memories/db/migrations/`: the Alembic environment and `versions/`. It ships inside the wheel; no
  `alembic.ini` is needed at runtime.
- Domain repositories keep their public classes and signatures (`OwnerDecisions`, `EditorialVerdicts`, the
  people registry, `RunDatabase`, ...). Only their internals move to SQLAlchemy Core over the store engine.

## Bootstrap

- `IMMICH_MEMORIES_DATABASE_URL` / `database.url` in `config.yaml`. Unset: `sqlite:///~/.immich-memories/store.db`
  (expanded per call, so a test or container can move `HOME`).
- `IMMICH_MEMORIES_DATABASE_SCHEMA` / `database.schema`, default `immich_memories`, PostgreSQL only.
- Bootstrap keys never come from the database. Neither does `IMMICH_MEMORIES_SECRET_KEY`.
- A URL is always logged redacted (`render_as_string(hide_password=True)`).

## Rules every table follows

- Portable types only: `String`/`Text` keys, `Integer`, `Float`, `Boolean`, `JSON`, `LargeBinary`, and
  `DateTime` holding naive UTC (`db.time.to_db` / `from_db` convert at the repository edge).
- No `ARRAY`, JSONB operators, `vector`, server-side functions or extensions.
- Upserts go through `db.upsert(conn, table, rows, keys, update=...)`, which picks the dialect's
  `insert().on_conflict_do_update`.
- Vectors are `LargeBinary` with `encoder_key` and `dim`; comparisons stay in numpy.
- Write transactions stay short: one `with store.begin() as conn:` per logical write.
- Every table is on the shared `MetaData`, so the schema name is translated in one place
  (`schema_translate_map={"immich_memories": None}` on SQLite, the configured schema on PostgreSQL).

## Engines

- SQLite: connect hook sets `journal_mode=WAL`, `busy_timeout=30000`, `synchronous=NORMAL`, `foreign_keys=ON`.
  The file is created at 0600. Opening a file on NFS, SMB or CIFS is refused unless
  `IMMICH_MEMORIES_ALLOW_NETWORK_SQLITE=1`, in which case it warns.
- PostgreSQL: psycopg 3, `pool_size=5`, `pool_pre_ping=True`, plain PostgreSQL 14+ with no extensions.
- One engine per (URL, schema) per process.

## Leases

- `db.leases.Lease(name, lock_path, store)`: `acquire(wait=False)` (raises `LeaseHeldError`),
  `release()`, `held_elsewhere()`, context manager. It is released when the holder dies.
- SQLite: the fcntl lock file at `lock_path`, as before the store existed.
- PostgreSQL: session `pg_try_advisory_lock(871_0002, hashtext(schema || ':' || name))` on a
  connection kept checked out for the lease's lifetime; the class is not the migration lock's
  `871_0001`, and the schema in the key keeps two stores in one database apart.
- Users: the automation lease, `PipelineLock`, the editorial attempt's liveness lease. Across hosts
  on PostgreSQL they coordinate through the database; nothing about a lease is stored in a table.

## Migrations

- One Alembic history, `render_as_batch=True`, version table `alembic_version` inside our schema,
  autogenerate filtered to our `MetaData`.
- Locked: `pg_advisory_lock` on PostgreSQL; an fcntl lock beside the file plus `BEGIN IMMEDIATE` on SQLite.
- The store is upgraded to every head when it opens. Downgrade exists for every revision and is tested
  on a populated store: each step down drops exactly the tables its revision created, rows and all
  (`0005_operations`: run history and special days; `0004_annotations`: model answers and owner
  decisions; `0003_settings`; `0002_people`; `0001_foundation`: `store_meta`), and every table below
  keeps its rows. So a rollback is a restore from backup, never a downgrade.
- One line of revisions: `0001_foundation` → `0002_people` → `0003_settings` → `0004_annotations` →
  `0005_operations`. A new revision's `down_revision` is the current head.

## The `immich_memories.db` API

Repositories use these and nothing lower:

- `open_store(config=None, *, location=None) -> Store`: resolve the location, build the engine,
  upgrade to head under the lock, cache per `(url, schema)`. `close_stores()` disposes them all.
- `Store`: `.engine`, `.begin()` (one write transaction; `BEGIN IMMEDIATE` on SQLite), `.connect()`,
  `.dialect_name`, `.schema` (the real PostgreSQL schema, `None` on SQLite), `.location`,
  `.applied` (revisions this open migrated).
- `resolve_location(config) -> StoreLocation`, `redact_url(url)`.
- `upsert(conn, table, rows, keys, update=None)`: `update=None` overwrites every non-key column,
  `update=()` is `ON CONFLICT DO NOTHING`.
- `to_db(datetime | iso str) -> naive UTC`, `from_db(naive) -> aware UTC`, `iso_from_db(naive) -> str`,
  `now_db()`. A naive value handed to `to_db` is taken to be UTC already.
- `connect_sqlite(path, private=True, ...)`: the raw `sqlite3` factory for the files that are not
  ported yet, and for the cache. `guard_sqlite_path`, `private_database_path` sit beside it.
- Migrations: `upgrade(store)`, `downgrade(store, target)`, `current_revisions(store)`, `heads()`,
  `revision_lineage(rev)`, `pending_changes(store)` (autogenerate's diff; empty when tables and
  revisions agree), `migration_schema()` (inside a revision), `FOUNDATION_REVISION`.
- `immich_memories.db.tables`: `metadata`, `SCHEMA`, and every table (`store_meta` so far).

## Adding a table

1. Declare it in `db/tables/<domain>.py` on `immich_memories.db.metadata.metadata` and import
   the module in `db/tables/__init__.py`.
2. Add `db/migrations/versions/<NNNN>_<domain>.py`. Until the slices are relinked into one line,
   each sets `down_revision = "0001_foundation"`. Every op passes `schema=migration_schema()`, never
   the symbolic `SCHEMA`: Alembic renders `ALTER` and a batch rebuild's rename with the name it
   is given, past `schema_translate_map`. Autogenerate against a scratch store helps
   (`alembic.ini` at the repo root, dev only), then replace the schema it wrote.
3. `tests/store/test_migrations.py` then checks up, down and `pending_changes() == []` on both
   backends, and that every head descends from the foundation.

## Import and cutover

- Each domain ships `import_legacy(store, home) -> ImportOutcome`, `legacy_sources(home) -> list[Path]`
  and `verify_legacy(store, home) -> list[str]` in its own module. `store/legacy_imports.IMPORTERS`
  lists the modules in dependency order (people, annotations, operations, banks); a new domain is one
  `LegacyImporter(name, module)` line.
- `run_import(store, home)` runs them in order. When one completes, `store_meta` gets
  `legacy_import:<name>` = the home, and path, size, mtime (ns) and SHA-256 of every source file; a
  later run skips an importer whose sources still match. When all complete, `legacy_import` records
  the whole import. Importers are idempotent (`ON CONFLICT DO NOTHING`, a held key keeps the store's
  row; a picture's face boxes commit together), so an interrupted run finishes on the next one and
  ends identical to a clean import.
- `store import --from <dir> [--verify]`: `--verify` re-reads every source and checks each legacy key
  is in the store with equal values; exactly for owner decisions, owner edits, people and special
  days, floats to within rounding elsewhere. An audience hold passes when the store's is the same or,
  under the same prompt, stricter (the import may tighten a hold, never loosen it). Exit 1 on any
  difference.
- The replay harness (`scripts/replay_editorial_routes.py`) fingerprints the store the replayed CLI
  reads (either backend, never migrated or created) and no legacy file; `scripts/setup_matrix_seed.py`
  empties every reader-answer table in a seeded cell's store (bank answers and text holds included)
  and deletes the legacy bank files, which only the import would read.
- **First open.** `import_on_first_open` is an `on_first_open` hook of `open_store`: it runs once per
  store per process, after the migration lock is released and outside the open lock. The CLI root
  and the UI's `main()` register it after the config has loaded, because loading the config opens
  the store (stored settings) and the operations importer reads the config: registering earlier
  would run an import inside a config load. `store` subcommands never register it. The hook reads
  `store_meta['legacy_import']` (one primary-key read) and returns when it exists; otherwise, if any
  importer finds a source under `IMMICH_MEMORIES_IMPORT_FROM` (default `~/.immich-memories`), it
  takes the `legacy-import` lease (a lock file beside the SQLite store, an advisory lock on
  PostgreSQL), reads the record again, and runs `run_import`. Two processes starting together import
  once. A failure is logged and leaves no record, so the next start retries. A `cache.db` counts as a
  source only while it still holds history tables, so a fresh install's cache never triggers it.
- Legacy files are opened read-only and never changed or deleted.
- Settings are the exception: nothing moves from `config.yaml` into the database without an explicit action.
- After cutover the store is authoritative. There are no dual writes and no fallback writes; legacy formats are
  read only by the importers (`grep -rn sqlite3 src/immich_memories` shows the cache, `db/` and the importers).

## Backup, restore, copy, status

- `store backup [--to FILE]`: SQLite `VACUUM INTO`; PostgreSQL `pg_dump --format=custom --schema=<schema>`
  on the snapshot the manifest's counts were read in (`pg_export_snapshot`). Manifest
  `<file>.manifest.json`: app version, revisions, backend, schema, counts, created_at. `pg_dump` comes
  from `PATH` (the image installs `postgresql-client`).
- `store restore --from FILE [--force]`: refuses a store holding rows without `--force` and a schema
  holding tables that are not ours always. SQLite: the file is staged beside the store and swapped in
  with every engine of the process disposed and the old `-wal`/`-shm` removed. PostgreSQL: the schema
  is dropped and `pg_restore --no-owner --no-acl` rebuilds it (renamed when the backup came from
  another schema name). A `pg_restore` newer than the server fails its `SET transaction_timeout`;
  that one error is tolerated. Then the store is migrated to head and its counts checked.
- `store copy --to URL [--schema S] [--force]`: target migrated to head, rows copied in 5,000-row
  batches parents first in one target transaction, PostgreSQL serial sequences advanced past the
  copied ids, then row counts and digests compared per table.
- `store status`: backend, redacted URL, schema, revisions and whether they are head, the import
  record, counts, file or schema size, and a network-filesystem warning. Reads without migrating.
- Digests (`db/inventory.py`) are the sum of one SHA-256 per row modulo 2**256 over backend-neutral
  values, so row order and backend never matter.

### Model answers and owner decisions (revision `0004_annotations`)

- Every table of `annotations.sqlite`, plus `judgments.db` and the `text-judgments.sqlite` a research attempt
  kept, is a store table with the file's primary key (`db/tables/annotations.py`, `db/tables/model_answers.py`).
  `assets` became `annotation_assets` and `flags` became `asset_flags`; `face_boxes` gained an `ordinal` key.
  Owner decisions are the `asset_flags` rows with `source='owner'`, one per picture.
- `store/legacy_annotations.import_legacy(store, home)` is the only reader of those files: `mode=ro`, keys kept,
  `ON CONFLICT DO NOTHING`, and an owner decision the store holds is never joined by the file's older one.
  `editorial.annotation_database` is deprecated: it names a legacy file to import, and its directory still holds
  `structure-banks/` (`EditorialConfig.resolve_bank_root`).
- Per-profile isolation (the setup matrix, any comparison harness) is one store per profile: set
  `IMMICH_MEMORIES_DATABASE_URL` (or `database.url`) per profile. `setup_matrix_plan.cache_pins` puts a
  `store.db` in each cell's cache directory.
- The detector worker runs in an interpreter without the app, so it appends decided rows to a JSON-lines spool
  and the parent banks them while it runs.

### JSON banks and owner review edits (revision `0006_banks`)

The rule: what is read back across films or runs, and that a model was paid for or the owner decided, is
store. What is recomputed from Immich or from the pictures is cache and stays a file. What one attempt writes
into its own directory stays a file.

| File | Class | Where it lives now |
|---|---|---|
| `structure-banks/audience-verdicts.private.json` | model answers + holds | `audience_answers`, `audience_holds` (`store/audience_bank.py`) |
| `structure-banks/<case>/memory-worthy.private.json`, `thesis-fit.private.json` | model answers (block votes) | `vote_bank_entries` (`store/vote_banks.py`) |
| `<film>.owner-edits-<id>.private.json` beside a film | owner decision | `owner_edits` (`store/owner_edits.py`) |
| `special-days.json` | owner decision | the operations slice |
| `place-names/<digest>.json`, `familiar-places/<digest>.json`, `trip-inputs/assets.json` | cache (geocoding, GPS clusters, asset lists) | files; `place-names` keeps `locked_file.file_lock` |
| `structure-banks/thumbnail-hashes.sqlite`, `scene-prints.sqlite` | cache | files |
| `music-mood.private.json`, plan, trace, status, render projection, stage progress, preparation, `album-index`, `motion-outcomes*`, `llm-usage.json` | per-attempt artifacts | files; the mood's model answer is a `judgments` row |
| `people-graph.json` | derived report, rewritten by every scan | file |

- The audience bank keeps the gate's rules: a hold is split by source into a `permanent` slot (a detector or a
  rule; nothing lifts it) and a `text` slot stamped with the audience prompt and check policy (a new prompt
  retires it, and only a reading under the new prompt replaces it). A hold only tightens. A refusal stands in
  the cut's bank at once and reaches the store in batches of up to 500 pictures (`AudienceBank.flush`, called
  when a batch fills and when the cut ends, failed or not): one transaction locks the batch's pictures in
  sorted order (`BEGIN IMMEDIATE` on SQLite, per-picture transaction advisory locks in ascending key order on
  PostgreSQL), reads their holds with one set-based query, merges in Python and upserts the changed slots in
  one statement. Overlapping batches queue instead of deadlocking, a refusal that changes nothing costs no
  write, and a crash loses at most the batch in hand. The no-model draft's refusals (`open_banked_facts`)
  read the bank through `library_refusals(store, audience)`.
- A vote bank is keyed by bank name and the film's case key (the old directory name), then by the block's
  question digest or, in the `rows` / `rows-one-order` sections, by the row's question digest. `VoteBank.save`
  writes only the entries changed since the last save; the file rewrote the whole bank after every block.
- Owner review edits are kept whole under an `edit_id`, with the film's stem and the reviewed attempt's id;
  `runs why` reads them back by attempt.
- `store/legacy_banks.import_legacy(store, home)` finds `structure-banks/` under the default cache directory
  and under `resolve_bank_root` of the configured cache and annotation database, and owner edit files under
  the output directory (`~` read as the directory `home` sits in). It keeps every key; a key the store holds
  keeps the store's value, except a hold: a legacy hold stricter than the store's in the same slot and under
  the same prompt tightens it. The files are read only, and a second run imports nothing.
- `locked_file.file_lock` stays for the place-name cache and the SQLite migration lock.
- Measured on a synthetic 20k-picture library (Apple Silicon): holding 20k pictures took 0.19 s on SQLite and
  0.42 s on native PostgreSQL 14 (the file took 33.4 s for 2k and grows quadratically; one transaction per hold
  took 30.4 s on SQLite). Re-holding all 20k with nothing new to write: 0.06 s and 0.08 s. Banking 20k vote rows
  in 1,667 block saves took 1.0 s in the store against 131 s for the file. Opening either bank at 20k: under
  0.6 s.
- With `IMMICH_MEMORIES_DATABASE_URL` naming a SQLite file (or a URL plus `IMMICH_MEMORIES_DATABASE_SCHEMA`),
  `resolve_location()` reads no `config.yaml`: the environment already decides the location.

## Settings

Precedence: env > `config.yaml` > database > default. The UI writes the database only and shows each key's
source; an env- or YAML-overridden key is read-only and names what overrides it. Secrets in the database are
encrypted with `IMMICH_MEMORIES_SECRET_KEY` (Fernet); without it the UI refuses to store a secret.

## Tests

- `make test-store-sqlite`: the `tests/store/` suite on SQLite, fast and local.
- `make test-store`: the same suite on SQLite and on PostgreSQL. PostgreSQL comes from
  `IMMICH_MEMORIES_TEST_DATABASE_URL`; locally the target starts a `postgres:16` container, and CI uses a
  `postgres:16` service.
- Each PostgreSQL test gets its own schema, dropped afterwards, so tests are isolated and the
  shared-schema case is exercised for free.
- The PostgreSQL backup drill needs `pg_dump`/`pg_restore` on `PATH`, at least the server's major.
  CI installs `postgresql-client-16` from PGDG and fails unless both report 16; `make test-store`
  refuses a missing or older client first (on a Mac, `brew install libpq` and put
  `$(brew --prefix libpq)/bin` first on `PATH`).
- Pre-beta acceptance lives in `tests/store/`: repeat and interrupted import (a child SIGKILLed
  mid-import, then rerun, equals a clean import), two processes starting together import once,
  rollback of a populated store revision by revision, schema isolation against namesakes of every
  table, the backup/restore drill, and `store copy` SQLite → PostgreSQL → SQLite.
