# The store: one versioned database on SQLite or PostgreSQL

Issue #871 holds the decision, the inventory with file:line and the dual-backend rules. This page is the
contract the code follows. When the two disagree, the issue's "Decision 2026-09-26" wins and this page is fixed.

## Two lifetimes

| | Store | Cache |
|---|---|---|
| Holds | human decisions, model answers someone paid for, run history, UI-edited settings | derived analysis, hashes, scene prints, geocoding |
| Backend | the configured URL: SQLite (default) or PostgreSQL | always local SQLite files |
| Schema changes | Alembic, one history for both backends | a version stamp; a mismatch drops and rebuilds |
| Backed up | yes (`store backup`) | no |

Media, previews, thumbnails and per-attempt artifacts stay files.

## Package layout

- `immich_memories/db/`: engine, bootstrap URL, the SQLite connection factory, the network-filesystem guard,
  the upsert helper, time helpers, migration runner and lock, backup/restore.
- `immich_memories/db/tables/<domain>.py`: SQLAlchemy `Table` objects on one shared `MetaData(schema="immich_memories")`.
- `immich_memories/db/migrations/`: the Alembic environment and `versions/`. It ships inside the wheel; no
  `alembic.ini` is needed at runtime.
- Domain repositories keep their public classes and signatures (`OwnerDecisions`, `EditorialVerdicts`, the
  people registry, `RunDatabase`, ...). Only their internals move to SQLAlchemy Core over the store engine.

## Bootstrap

- `IMMICH_MEMORIES_DATABASE_URL` / `database.url` in `config.yaml`. Unset: `sqlite:///~/.immich-memories/store.db`
  (expanded per call, so a test or container can move `HOME`).
- `IMMICH_MEMORIES_DATABASE_SCHEMA` / `database.schema`, default `immich_memories`, PostgreSQL only.
- Bootstrap keys never come from the database. Neither does `IMMICH_MEMORIES_SECRET_KEY`.
- A URL is always logged redacted (`render_as_string(hide_password=True)`).

## Rules every table follows

- Portable types only: `String`/`Text` keys, `Integer`, `Float`, `Boolean`, `JSON`, `LargeBinary`, and
  `DateTime` holding naive UTC (`db.time.to_db` / `from_db` convert at the repository edge).
- No `ARRAY`, JSONB operators, `vector`, server-side functions or extensions.
- Upserts go through `db.upsert(conn, table, rows, keys, update=...)`, which picks the dialect's
  `insert().on_conflict_do_update`.
- Vectors are `LargeBinary` with `encoder_key` and `dim`; comparisons stay in numpy.
- Write transactions stay short: one `with store.begin() as conn:` per logical write.
- Every table is on the shared `MetaData`, so the schema name is translated in one place
  (`schema_translate_map={"immich_memories": None}` on SQLite, the configured schema on PostgreSQL).

## Engines

- SQLite: connect hook sets `journal_mode=WAL`, `busy_timeout=30000`, `synchronous=NORMAL`, `foreign_keys=ON`.
  The file is created at 0600. Opening a file on NFS, SMB or CIFS is refused unless
  `IMMICH_MEMORIES_ALLOW_NETWORK_SQLITE=1`, in which case it warns.
- PostgreSQL: psycopg 3, `pool_size=5`, `pool_pre_ping=True`, plain PostgreSQL 14+ with no extensions.
- One engine per (URL, schema) per process.

## Leases

- `db.leases.Lease(name, lock_path, store)`: `acquire(wait=False)` (raises `LeaseHeldError`),
  `release()`, `held_elsewhere()`, context manager. It is released when the holder dies.
- SQLite: the fcntl lock file at `lock_path`, as before the store existed.
- PostgreSQL: session `pg_try_advisory_lock(871_0002, hashtext(schema || ':' || name))` on a
  connection kept checked out for the lease's lifetime; the class is not the migration lock's
  `871_0001`, and the schema in the key keeps two stores in one database apart.
- Users: the automation lease, `PipelineLock`, the editorial attempt's liveness lease. Across hosts
  on PostgreSQL they coordinate through the database; nothing about a lease is stored in a table.

## Migrations

- One Alembic history, `render_as_batch=True`, version table `alembic_version` inside our schema,
  autogenerate filtered to our `MetaData`.
- Locked: `pg_advisory_lock` on PostgreSQL; an fcntl lock beside the file plus `BEGIN IMMEDIATE` on SQLite.
- The store is upgraded to every head when it opens. Downgrade exists for every revision and is tested.
- A single head is asserted by a test once the parallel slices are relinked; until then the test
  asserts that every head descends from `0001_foundation`.

## The `immich_memories.db` API

Repositories use these and nothing lower:

- `open_store(config=None, *, location=None) -> Store`: resolve the location, build the engine,
  upgrade to head under the lock, cache per `(url, schema)`. `close_stores()` disposes them all.
- `Store`: `.engine`, `.begin()` (one write transaction; `BEGIN IMMEDIATE` on SQLite), `.connect()`,
  `.dialect_name`, `.schema` (the real PostgreSQL schema, `None` on SQLite), `.location`,
  `.applied` (revisions this open migrated).
- `resolve_location(config) -> StoreLocation`, `redact_url(url)`.
- `upsert(conn, table, rows, keys, update=None)`: `update=None` overwrites every non-key column,
  `update=()` is `ON CONFLICT DO NOTHING`.
- `to_db(datetime | iso str) -> naive UTC`, `from_db(naive) -> aware UTC`, `iso_from_db(naive) -> str`,
  `now_db()`. A naive value handed to `to_db` is taken to be UTC already.
- `connect_sqlite(path, private=True, ...)`: the raw `sqlite3` factory for the files that are not
  ported yet, and for the cache. `guard_sqlite_path`, `private_database_path` sit beside it.
- Migrations: `upgrade(store)`, `downgrade(store, target)`, `current_revisions(store)`, `heads()`,
  `revision_lineage(rev)`, `pending_changes(store)` (autogenerate's diff; empty when tables and
  revisions agree), `migration_schema()` (inside a revision), `FOUNDATION_REVISION`.
- `immich_memories.db.tables`: `metadata`, `SCHEMA`, and every table (`store_meta` so far).

## Adding a table

1. Declare it in `db/tables/<domain>.py` on `immich_memories.db.metadata.metadata` and import
   the module in `db/tables/__init__.py`.
2. Add `db/migrations/versions/<NNNN>_<domain>.py`. Until the slices are relinked into one line,
   each sets `down_revision = "0001_foundation"`. Every op passes `schema=migration_schema()`, never
   the symbolic `SCHEMA`: Alembic renders `ALTER` and a batch rebuild's rename with the name it
   is given, past `schema_translate_map`. Autogenerate against a scratch store helps
   (`alembic.ini` at the repo root, dev only), then replace the schema it wrote.
3. `tests/store/test_migrations.py` then checks up, down and `pending_changes() == []` on both
   backends, and that every head descends from the foundation.

## Import and cutover

- `store import --from <dir> [--verify]` reads legacy files read-only: `people.yaml`, `special-days.json`,
  `cache.db` store tables, `judgments.db`, `annotations.sqlite`, JSON banks, the run index. It records what it
  imported (source path, size, mtime, sha256) and is idempotent and resumable.
- When the store opens empty and legacy files exist, the same import runs once automatically, so an upgrade
  keeps every decision. It never deletes or rewrites a legacy file.
- Settings are the exception: nothing moves from `config.yaml` into the database without an explicit action.
- After cutover the store is authoritative. There are no dual writes and no fallback writes; legacy formats are
  read only by the importer.

### Model answers and owner decisions (revision `0004_annotations`)

- Every table of `annotations.sqlite`, plus `judgments.db` and the `text-judgments.sqlite` a research attempt
  kept, is a store table with the file's primary key (`db/tables/annotations.py`, `db/tables/model_answers.py`).
  `assets` became `annotation_assets` and `flags` became `asset_flags`; `face_boxes` gained an `ordinal` key.
  Owner decisions are the `asset_flags` rows with `source='owner'`, one per picture.
- `store/legacy_annotations.import_legacy(store, home)` is the only reader of those files: `mode=ro`, keys kept,
  `ON CONFLICT DO NOTHING`, and an owner decision the store holds is never joined by the file's older one.
  `editorial.annotation_database` is deprecated: it names a legacy file to import, and its directory still holds
  `structure-banks/` (`EditorialConfig.resolve_bank_root`).
- Per-profile isolation (the setup matrix, any comparison harness) is one store per profile: set
  `IMMICH_MEMORIES_DATABASE_URL` (or `database.url`) per profile. `setup_matrix_plan.cache_pins` puts a
  `store.db` in each cell's cache directory.
- The detector worker runs in an interpreter without the app, so it appends decided rows to a JSON-lines spool
  and the parent banks them while it runs.

## Settings

Precedence: env > `config.yaml` > database > default. The UI writes the database only and shows each key's
source; an env- or YAML-overridden key is read-only and names what overrides it. Secrets in the database are
encrypted with `IMMICH_MEMORIES_SECRET_KEY` (Fernet); without it the UI refuses to store a secret.

## Tests

- `make test-store-sqlite`: the `tests/store/` suite on SQLite, fast and local.
- `make test-store`: the same suite on SQLite and on PostgreSQL. PostgreSQL comes from
  `IMMICH_MEMORIES_TEST_DATABASE_URL`; locally the target starts a `postgres:16` container, and CI uses a
  `postgres:16` service.
- Each PostgreSQL test gets its own schema, dropped afterwards, so tests are isolated and the
  shared-schema case is exercised for free.
